## The main entry points

Read the Rust core as a pipeline:

1. Public APIs in `Automerge` and `AutoCommit` accept local changes, sync
   messages, or saved bytes.
2. Changes become imported operations against actor and object indexes.
3. The change graph records causal history and heads.
4. The op set answers materialized state queries.
5. Patch logs optionally describe how a caller should update a view.

<SourceCard path="rust/automerge/src/automerge.rs">
This is the lower-level document API. Look for `apply_changes`, load/save
paths, `receive_sync_message_log_patches`, and bundle helpers.
</SourceCard>

<SourceCard path="rust/automerge/src/autocommit.rs">
This wrapper owns automatic transactions, isolation, integration, patch logs,
and the sync trait implementation used heavily by application code.
</SourceCard>

## Where malformed input becomes dangerous

Most desktop-patches fixes move checks earlier. That pattern matters more than
any single error type. A good boundary rejects a malformed change before it:

- inserts new actors into the op set
- imports operations
- updates history
- exposes a patch log
- lets hydrate/read APIs observe invalid state

<Callout title="Patch-stack pattern" tone="proof">
Many fixes are preflight validations. They turn "panic after partial mutation"
or "invalid state accepted" into "typed error before mutation."
</Callout>

## Practical reading order

Start with a test name from the bug lab. Read the test first, then the changed
validator, then the caller that invokes the validator before mutation. This is
usually faster than starting at the public API and following every abstraction.
